# Atmeex Cloud — интеграция для Home Assistant

*[English version](README.md)*

## О чём это

Интеграция подключает бризеры Atmeex (AirNanny) к [Home Assistant](https://www.home-assistant.io/):
управление и показания прямо на дашбордах и в автоматизациях. Работает через официальный
REST API Atmeex Cloud (`https://api.iot.atmeex.com`), а начиная с 0.6.0 умеет ещё и
разговаривать с бризером напрямую по локальной сети.

🧩 Написано и поддерживается Сергеем Полуновским: собственный клиент к актуальному API
Atmeex, рассчитанный на современные выпуски Home Assistant.

## Возможности

* Все устройства аккаунта подхватываются сами.
* Включение и выключение, семь скоростей вентилятора.
* Режимы заслонки: приток, рециркуляция, смешанный.
* Целевая температура нагрева.
* Увлажнитель — на тех модификациях, где он есть; определяется автоматически.
* Пресеты «Авто» и «Сон».
* Датчики: температура в помещении и на улице всегда, CO₂ и влажность — на тех
  модификациях, где эти узлы стоят.
* Повторный вход при истечении токена — штатным мастером Home Assistant, без правки
  конфигов.
* Онлайн-статус прямо на карточке климата.
* Локальный канал: мгновенные показания и работа при аварии облака.

## Установка

**Через HACS (рекомендуется)**

1. HACS → Интеграции → Пользовательские репозитории.
2. Добавить `https://github.com/pols1/hass-atmeex-cloud`, тип — Integration.
3. Найти Atmeex Cloud, установить.
4. Перезапустить Home Assistant.

**Вручную:** скопировать папку `custom_components/atmeex_cloud` в `/config/custom_components/`
и перезапустить Home Assistant.

## Настройка

Настройки → Устройства и службы → Добавить интеграцию → Atmeex Cloud → почта и пароль от
аккаунта Atmeex. Все привязанные бризеры появятся сами.

Опрос облака идёт раз в 30 секунд. С включённым локальным каналом показания приходят
потоком, каждые несколько секунд.

## Опции

Настройки → Устройства и службы → Atmeex Cloud → **Настроить**.

### Какие узлы есть именно у вашего бризера

A7 продаётся семью модификациями, и начинка у них разная:

| Модификация | Увлажнитель | Датчик CO₂ |
|---|---|---|
| Simple, Flow | — | — |
| Start | есть | — |
| BabyCare, Forever (3 цвета) | есть | есть |

Ни облачный API, ни само устройство модификацию не сообщают: `model` всегда `A7`. Поэтому
интеграция определяет её по показаниям, и переключатели **Датчик CO₂** и **Увлажнитель**
по умолчанию стоят в положении *авто*:

* **CO₂** — отсутствующий датчик отдаёт ровно `0 ppm` и не меняется никогда. В воздухе
  такого не бывает: на улице около 420 ppm, в помещении 500–1500. Замерено на живом Start —
  1952 кадра телеметрии, во всех ноль. Значит устойчивый ноль означает, что датчика нет, и
  вечно нулевая сущность не создаётся.
* **Увлажнитель** — влажность в помещении приходит только от моделей, где он есть. Наличие
  поля `hum_stg` ничего не доказывает: его шлют и те модификации, которым увлажнять нечем.

Определение только добавляет узел и никогда его не отзывает, поэтому секундный ноль от
сбойного датчика не удалит сущность вместе с историей. Положения *on* и *off* перебивают
автоматику — на случай неисправного датчика или нестандартной сборки.

**Режим охлаждения** остаётся ручным: линейка A7 не охлаждает, опция существует для других
климатических комплексов Atmeex.

### Путь команд

* `cloud_first` (по умолчанию) — команда идёт через облако, а если облако её не приняло и
  устройство на связи локально, уходит напрямую.
* `local_first` — сначала напрямую устройству, облако используется, только когда бризер не
  подключён к Home Assistant.
* `cloud_only` — локальный канал для записи не используется вовсе.

Облако первично не из-за надёжности, а ради согласованности: приложение вендора читает
состояние оттуда, и запись мимо него развела бы две картины.

## Совместимость

Проверено на **Home Assistant 2026.8** (Python 3.14, Home Assistant OS); в `hacs.json`
объявлен минимум 2026.7 — в этой версии появился `UnitOfRatio`. Интеграция использует
актуальные механизмы ядра: общая сессия aiohttp, `DataUpdateCoordinator`, повторная
авторизация через config entry, мастер опций, берущий `config_entry` у ядра.

Диалоги настройки переведены: английский и русский лежат в
`custom_components/atmeex_cloud/translations/`.

Каждый push проверяется hassfest, валидацией HACS и тестами — см.
[.github/workflows/validate.yml](.github/workflows/validate.yml).

## Сущности

Поднимаются две платформы: `climate` и `sensor`.

| Тип | Пример | Что это |
|---|---|---|
| **climate** | `climate.brizer_bedroom` | Основная сущность: питание, скорость 1–7, целевая температура, пресеты, слайдер увлажнения, режим заслонки |
| **sensor** | `sensor.brizer_bedroom_indoor_temperature` | Температура в помещении |
| **sensor** | `sensor.brizer_bedroom_outdoor_temperature` | Температура на улице |
| **sensor** | `sensor.brizer_bedroom_co2` | CO₂ в ppm — только там, где есть датчик |
| **sensor** | `sensor.brizer_bedroom_humidity` | Влажность в помещении — только там, где есть увлажнитель |

Онлайн-статус отдельной сущностью не выносится: он управляет доступностью климат-сущности,
поэтому офлайн-устройство просто гаснет на карточке.

`select.py` и `fan.py` лежат в репозитории, но **не подключены** — в `PLATFORMS` только
`CLIMATE` и `SENSOR`. Включите их там, если хотите заслонку и ступень увлажнения
отдельными сущностями.

## Локальный канал

Бризер не слушает ни одного порта — проверено полным сканом TCP (1–10000, все порты
`closed`) и UDP-зондированием. Он чистый исходящий клиент: открывает одно TCP-соединение к
`ws.iot.atmeex.com:3001` и говорит по нему голым JSON, без TLS. Поэтому локальный доступ —
это оказаться на приёмном конце его соединения, а не подключиться к устройству.

С включённым **локальным каналом** Home Assistant слушает порт 3001 и **передаёт весь поток
в облако Atmeex без изменений**: приложение вендора продолжает работать, а интеграция
попутно читает те же данные. Устройство шлёт состояние каждые несколько секунд, поэтому
сущности обновляются почти мгновенно вместо опроса раз в 30 секунд, и в потоке видны
влажность и флаг бачка увлажнителя.

Если облако недоступно, канал отвечает устройству сам — бризер молчит, пока сервер не
подтвердит его `hello` синхронизацией времени. Показания при аварии вендора продолжают идти,
а как только облако возвращается, сессия рвётся, и устройство переподключается уже сквозным
путём.

### Как завернуть трафик

Само заворачивание интеграция сделать не может — это разовая правка в сети. Способа два, и
на железе, где всё это писалось, работал только первый.

**По адресу (рекомендуется).** Правило NAT ловит устройство независимо от того, как оно
разрешает имена: сравнивается адрес назначения. На MikroTik, для каждого бризера:

```
/ip firewall nat add chain=dstnat protocol=tcp src-address=<IP_БРИЗЕРА> \
    dst-address=<IP_ОБЛАКА> dst-port=3001 \
    action=dst-nat to-addresses=<IP_HA> to-ports=3001 \
    comment="atmeex-local" place-before=0
/ip firewall nat add chain=srcnat protocol=tcp src-address=<IP_БРИЗЕРА> \
    dst-address=<IP_HA> dst-port=3001 action=masquerade comment="atmeex-local"
```

Второе правило обязательно, когда бризер и Home Assistant в одном bridge: без него ответ
уйдёт с чужого адреса источника и устройство порвёт сессию.

**По имени.** Статическая запись `ws.iot.atmeex.com` на адрес Home Assistant проще и
работает на любом роутере, Pi-hole или AdGuard Home. Здесь она не сработала: при живой и
включённой записи передёрнутый бризер всё равно ушёл прямо к вендору. Почему — не выяснено
до конца: DNS-запросы роутеру устройство шлёт, но именно про это имя мы его за руку не
поймали, так что оно может отвечать себе из кеша. Попробовать можно, но потом передёрните
устройство и посмотрите, куда оно приземлилось; если снова у вендора — переходите на
правило NAT.

### Предохранитель

Какой бы способ вы ни выбрали, его нужно сторожить. Пока заворачивание действует, простой
Home Assistant отрезает бризеры и от облака, причём надолго: устройство держит одно
соединение сутками. Это не теория — здесь так и вышло, полтора суток, пока сторожа не было.

```
/tool netwatch add name=atmeex-ha-guard type=tcp-conn host=<IP_HA> port=3001 \
    interval=30s timeout=3s \
    up-script="/ip firewall nat enable [find comment~\"atmeex-local\"]" \
    down-script="/ip firewall nat disable [find comment~\"atmeex-local\"]"
```

Именно выключать, а не удалять — тогда возврат мгновенный. Проверено на живой установке
целиком: канал остановлен, сторож заметил это за семь секунд, правила ушли в выключенные,
и оба бризера всё это время держали прямые сессии с вендором; после запуска канала всё
вернулось так же быстро.

**Проверка должна быть дешёвой.** Сторож раз в тридцать секунд открывает соединение к
локальному каналу. Если ответ на неё заставляет Home Assistant делать настоящую работу — как
было, пока канал на каждое входящее соединение лез в облако, — проверка не укладывается в
собственный таймаут, и сторож объявляет живой сервис мёртвым. Сторож, который на каждый стук
гоняет хозяина в подвал, рано или поздно решит, что дома никого нет.

**Перезапуск Home Assistant стоит вам канала на некоторое время.** Сторож опрашивает порт
раз в тридцать секунд, поэтому перезапуска на пару минут достаточно, чтобы он снял
заворачивание, — а устройства, переподключившись напрямую к вендору, останутся там до
своего следующего переподключения, а это может быть и через сутки. Ничего не ломается,
просто локальный канал всё это время простаивает. Учитывайте это при обновлениях или
передёрните устройство, если хотите вернуть его сразу.

### Чего ожидать при переключении

* Устройства переезжают при следующем переподключении, а не сразу: каждое держит одно
  соединение сутками. Передёргивание питания ускоряет, иначе просто подождите.
* Снятие старого заворачивания текущую сессию тоже не рвёт — таблица соединений помнит
  трансляцию до переподключения.
* Пока заворачивание работает, вендор по-прежнему видит устройства онлайн: Home Assistant
  передаёт их трафик без изменений.
* Подмена DNS, если вы её используете, действует и на сам Home Assistant. В этом случае
  интеграция берёт адрес облака по имени REST API и отвергает соединения, пришедшие с
  собственного исходящего сокета, — иначе канал соединялся бы сам с собой, принимал это за
  новое устройство и открывал следующее встречное, и так без конца.

## Увлажнитель

Там, где увлажнитель есть, под карточкой климата появляется слайдер влажности с четырьмя
ступенями — промежуточные значения прилипают к ближайшей:

| Слайдер | Ступень |
|---|---|
| 0 % | Выключено |
| 33 % | Первая |
| 66 % | Вторая |
| 100 % | Третья |

## Если что-то не так

| Симптом | Причина | Что делать |
|---|---|---|
| Интеграция не загружается | Старые или битые файлы | Переустановить из HACS |
| Ошибка входа при настройке | Неверные учётные данные | Проверить почту и пароль от Atmeex |
| Температура показывает −100 °C | API не вернул температуру помещения | Дождаться следующего обновления или перезапустить Home Assistant |
| Второй бризер не появился | API вернул `null` в condition | Исправлено в свежих выпусках |
| Сущности `unavailable`, в логе таймауты | Лежит само облако Atmeex | Проверять облако, а не интеграцию: `curl -m 10 https://api.iot.atmeex.com/`. С 0.5.10 причина пишется словами, а не пустым `Unexpected error:` |
| Кнопка «Настроить» ничего не делает | Исправлено в 0.5.10 | Обновить интеграцию |

Подробный лог: Настройки → Система → Журналы → `custom_components.atmeex_cloud`.

## Разработка

```
git clone https://github.com/pols1/hass-atmeex-cloud.git
cd hass-atmeex-cloud
python3 -m unittest discover -s tests -v
```

Тесты локального канала не требуют установленного Home Assistant: `local_channel.py`
намеренно не зависит ни от чего, кроме стандартной библиотеки, а фикстуры — настоящие
кадры, снятые с живого A7. Они же прогоняются в CI на каждый push. Остальное (облачный API,
сущности, мастер настройки) пока проверяется на живом Home Assistant.

### Выпуск версии

1. Поднять `version` в `manifest.json`.
2. Добавить раздел в `CHANGELOG.md`.
3. Закоммитить и запушить.
4. Поставить тег и отправить его:
   `git tag -a v0.6.0 -m "Release 0.6.0"` и `git push --tags`.
5. Создать GitHub Release — HACS предлагает обновления по опубликованным релизам, коммит в
   `main` до пользователей не доедет.
